# Implementation Plan: Ultra-Optimized Rust Proxy Benchmark vs. Traefik v3.7.12 (Rust 2024 / 1.97)

This document specifies the technical design, crate architecture, maximum release/SIMD/PGO compiler optimizations, profiling integration, and execution plan for a **benchmark crate** within the `lb` application workspace, comparing **Hyper**, **Cloudflare Pingora**, and **Monoio** against **Traefik v3.7.12** on **local Kubernetes (`kind`)** and standalone bare-metal in **Rust 2024 (rustc 1.97)**.

> [!IMPORTANT]
> The benchmark suite is structured as a **first-class crate** (`crates/bench`) within the `lb` workspace from day one. Proxy candidate implementations live as sibling crates that the bench crate depends on. This ensures the benchmark infrastructure is reusable, testable, and grows naturally alongside the main proxy application.

## 4. Maximum Release, PGO, BOLT & Compiler Optimizations

### 4.1. Compiler Vectorization Flags
```bash
export RUSTFLAGS="-C target-cpu=native -C llvm-args=-inline-threshold=600"
```

### 4.2. Profile-Guided Optimization (PGO) Pipeline

Three-pass build automated in `scripts/build_pgo.sh`:
```bash
#!/bin/bash
set -euo pipefail
CANDIDATE=${1:?Usage: build_pgo.sh <lb-proxy-hyper|lb-proxy-pingora|lb-proxy-monoio>}
PROFDATA_DIR="target/pgo-profiles"

echo "=== Pass 1: Instrumented build ==="
rm -rf "$PROFDATA_DIR" && mkdir -p "$PROFDATA_DIR"
RUSTFLAGS="-C target-cpu=native -Cprofile-generate=$PROFDATA_DIR" \
    cargo build --release --bin "$CANDIDATE"

echo "=== Pass 2: Profile collection ==="
./target/release/"$CANDIDATE" --mode standalone --config examples/pgo_routes.yaml &
PROXY_PID=$!; sleep 2
cargo run --release --bin lb-bench -- --mode local --target localhost:8080 \
    --concurrency 100,500,1000 --duration 10s --payload-sizes 1k,64k --warmup 2s
kill $PROXY_PID; wait $PROXY_PID 2>/dev/null || true

echo "=== Merge profiles ==="
llvm-profdata merge -o "$PROFDATA_DIR/merged.profdata" "$PROFDATA_DIR"

echo "=== Pass 3: PGO-optimized build ==="
RUSTFLAGS="-C target-cpu=native -Cprofile-use=$PROFDATA_DIR/merged.profdata" \
    cargo build --release --bin "$CANDIDATE"
```

### 4.3. BOLT Post-Link Optimization (Linux Only)
```bash
perf record -e cycles:u -j any,u -o perf.data -- ./target/release/lb-proxy-hyper &
# Run representative load ...
perf2bolt -p perf.data -o perf.fdata ./target/release/lb-proxy-hyper
llvm-bolt ./target/release/lb-proxy-hyper -o ./target/release/lb-proxy-hyper.bolt \
    -data=perf.fdata -reorder-blocks=ext-tsp -reorder-functions=hfsort \
    -split-functions -split-all-cold -dyno-stats
```

> [!NOTE]
> BOLT is Linux-only (`llvm-bolt` from LLVM 17+). Auto-skipped on macOS.

## 6. Monoio + kube-rs Hybrid Runtime Architecture

> [!IMPORTANT]
> `kube-rs` requires Tokio. The Monoio candidate uses a **split-runtime design**: dedicated Tokio thread for control plane, Monoio thread-per-core workers for data plane, communicating via `ArcSwap`.

```rust
fn main() {
    let route_table = Arc::new(ArcSwap::from_pointee(RouteTable::empty()));

    // Dedicated Tokio thread for kube-rs control plane
    let rt_clone = route_table.clone();
    std::thread::spawn(move || {
        tokio::runtime::Builder::new_current_thread()
            .enable_all().build().unwrap()
            .block_on(run_k8s_controller(rt_clone));
    });

    // Monoio thread-per-core data plane workers
    for cpu in 0..num_cpus::get() {
        let rt = route_table.clone();
        std::thread::spawn(move || {
            monoio::RuntimeBuilder::<monoio::FusionDriver>::new()
                .enable_all().build().unwrap()
                .block_on(run_proxy_worker(cpu, rt));
        });
    }
}
```

- **Concurrency**: 100, 1,000, 5,000, 10,000, 25,000.

- Measure RSS Memory: Go GC vs. Rust jemalloc.

- Steady 20,000 RPS + HTTPRoute mutations at 10-500 Hz.

- `matchit` vs `route-recognizer`.
- `ArcSwap` vs `parking_lot::RwLock` vs `tokio::sync::RwLock`.
- `simdutf8` vs `std::str::from_utf8`.

### Scenario 5: PGO Impact Delta
- Standard release vs. PGO-optimized on identical Scenario 1 workloads.

## 9. Phased Implementation Roadmap

### Phase 1: Workspace & `lb-core` Crate
1. Initialize Cargo workspace (`Rust 2024`, `rustc 1.97.1`) with `rust-toolchain.toml`, release profiles, and `[workspace.dependencies]`.
2. Build `crates/core` (`lb-core`):
   - `route_table.rs`: `ArcSwap<matchit 0.9::Router>` wrapper with hostname matching.
   - `target.rs`: Upstream endpoints, Round-Robin / Weighted load balancer.
   - `filter.rs`: Gateway API header modifiers and URL rewrite.
   - `alloc.rs`: `jemalloc` / `mimalloc` allocator setup module.
3. Unit tests for route matching and load balancing.

### Phase 2: `lb-bench` Crate — Harness, Metrics & Mock
1. Build `crates/bench` (`lb-bench`) as a library + binary crate.
2. Implement `harness/`: runner lifecycle, warm-up protocol, scenario definitions.
3. Implement `load/`: async HTTP load generator + standardized payloads.
4. Implement `metrics/`: `HdrHistogram 7.6` latency recorder, CPU/RSS sampler, hardware auto-detection.
5. Implement `mock/`: ultra-fast mock upstream HTTP echo server.
6. Implement `report/`: Markdown, CSV, and hardware spec report generators.
7. Build workspace-level Criterion microbenchmarks (`benches/`).

### Phase 3: Proxy Candidate Crates
1. **`crates/proxy-hyper`** (`lb-proxy-hyper`):
   - Library + binary. `jemalloc 0.7`, `TCP_NODELAY`, `SO_REUSEPORT`, `hyper 1.11` + `tokio 1.53`.
   - SIMD parsing + `ArcSwap<matchit 0.9>` + `kube 4.2` Gateway API reconciler.
2. **`crates/proxy-pingora`** (`lb-proxy-pingora`):
   - Library + binary. `jemalloc 0.7`, `pingora 0.8` engine + `matchit 0.9` + `kube 4.2`.
3. **`crates/proxy-monoio`** (`lb-proxy-monoio`):
   - Library + binary. `mimalloc 0.1.52`, hybrid Tokio/Monoio runtime, `kube 4.2`.
4. Wire all proxy crates as dependencies of `lb-bench`.

### Phase 4: PGO, Profiling & Flamegraph Tooling
1. Write `scripts/build_pgo.sh`, `scripts/build_bolt.sh`.
