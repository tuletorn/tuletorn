Measured on an 8-core kernel-7.0 host 28 Aug 2026

Beating Hyper

Four io_uring topologies under Hyper all lost to plain Tokio + epoll. Batching the submissions got one of them ahead by 7%. Throwing Hyper out of the data plane entirely got to 2.2–2.9×. This is the route, and what each step was actually worth.

Result

On the same two cores, with the origin and load generator held clear of saturation, a completion-native io_uring proxy runs 2.2× to 2.9× the throughput of Hyper + epoll, with a p99 seven times lower at high concurrency.

  • −16% Porting io_uring under Hyper loses. The best of four topologies reached 84% of baseline; the worst reached 30%.
  • +58% Batching submissions — one io_uring_enter per scheduler batch instead of one per operation — was worth up to 58% on its own, and put the best topology 7% ahead of Hyper.
  • 292% Removing Hyper from the data plane and driving hand-written state machines directly off completions reached 292% of baseline at c=1000, and won at every payload size from 1 KiB to 1 MiB.

Experiment

One binary, four topologies, identical request work

To make the comparison mean anything, I first pulled the per-request work — route lookup, backend selection, URI reassembly, hop-by-hop header hygiene — into a single shared function in lb-core, and refactored the existing Hyper candidate onto it. Every candidate now provably does the same work per request, so a throughput difference reflects the runtime rather than the handler.

The io_uring candidates are one binary with the topology selected by flag, so the scheduler and the ring layout are the only variables between them. All of them run the same Hyper HTTP/1.1 stack, the same jemalloc, and route every upstream hop over the ring too — no candidate is secretly half epoll.

Core budget

Four cores total: the proxy is pinned to cores 0–1 with two workers, the origin to core 2, the load generator (oha) to core 3. Every row below was checked for saturation — the proxy is the bottleneck only when it is near its 200% ceiling while the origin and generator still have headroom. Rows where that did not hold are labelled, not quietly reported as proxy results.

Mechanism

Why completion I/O loses under a readiness runtime

io_uring is a completion interface: the kernel owns a submitted buffer until its CQE arrives. AsyncRead is a readiness interface: the caller owns the buffer and expects the I/O to happen inside poll_read. Bridging the two forces the reactor to own every in-flight buffer, and it forces a task wakeup where epoll would have returned inline.

That accounts for the thread-per-core gap. The work-stealing collapse has a second cause on top: a stolen task submits to a ring owned by another thread, so the ring needs a lock, and with a single shared ring one driver task must reap every completion in the process. Giving each worker its own ring recovered part of it — 17,275 to 21,980 rps at c=256 — but nowhere near enough, because stealing still scatters submissions across rings.

The decisive test

Remove the submit syscall and the gap mostly closes

If the cost really is the io_uring_enter on every submission, then IORING_SETUP_SQPOLL — which hands the submission queue to a kernel poller thread so userspace never enters the kernel to submit — should recover it. It does, dramatically, and it is the single most informative number in this whole exercise.

Work-stealing over per-worker rings goes from 21,127 to 52,110 rps — a 2.5× jump from deleting one syscall per operation. That is conclusive about where its time went: it was never the copy or the waker, it was enter, and holding a lock across it. And thread-per-core with SQPOLL reaches 58,283 rps, 6% above the epoll baseline — the only configuration in the sweep that beat Hyper.

Why that 6% does not settle it

The SQPOLL rows draw 202–205% CPU against a 200% budget. I did not set IORING_SETUP_SQ_AFF, so the kernel poller threads are not confined by the proxy's taskset — they spill onto the cores running the origin and the load generator, and some of their time is not billed to the proxy at all. The win is real but it was bought with CPU the other candidates were not given.

The inversion at c=64 is the tell: SQPOLL hurts thread-per-core there, dropping it from 94% to 60% of baseline. A kernel poller only pays for itself while the ring stays busy enough to keep it from parking; below that threshold you pay for wakeups plus a thread competing for the same cores. SQPOLL is not a free win, it is a trade that needs load to justify it.

Hypothesis retired

Share-nothing placement was not the bottleneck

I expected static SO_REUSEPORT placement to hurt: the kernel hashes connections to accept queues without regard for load, so one core can sit on slow work while another idles. So I built a dispatcher that hands each accepted connection to the least-loaded core, scored by in-flight requests, with hysteresis to avoid pointless migration.

It made almost no difference — 48,682 against 49,338 rps at c=64, inside run-to-run noise. The only place it showed up at all was c=8, where the hash has few connections to spread and imbalance is real: 42,893 against 41,441, about 3.5%. Real, but nowhere near the size of the gap that matters. Connection-level placement is the wrong knob when the cost is per-operation.

Prior art

What Arc does instead

Arc is a ~57k-line io_uring gateway that takes the other road: it has no async runtime at all. Its worker is a bare loop — submit_and_wait(1), drain every CQE, dispatch each one to a hand-written state machine — and it ships its own HTTP/1 and HTTP/2 implementations rather than sitting on Hyper. That single decision is what unlocks the six mechanisms below, all of which my adapter structurally cannot use.

SQE batching Arcpush_sqe writes the ring with no syscall; one io_uring_enter covers the whole accumulated batch. MineOne enter per operation. The SQPOLL result above measures exactly what this costs: up to 2.5× throughput.
Registered buffers Arcread_fixed/write_fixed against a pre-registered, page-touched pool with intrusive refcounts for zero-copy splitting. MineA per-connection Vec plus a copy into the caller's buffer on every read.
Registered files Arcregister_files with IOSQE_FIXED_FILE: no fd table lookup per operation. MineRaw fds, resolved by the kernel on every submission.
Multishot accept ArcOne SQE serves many accepts, with a runtime downgrade if the kernel returns EINVAL. MineOne accept SQE per connection.
No waker machinery ArcCQE user_data packs op kind, side, slab index and a generation counter; the handler advances the connection directly. MineEvery completion goes eventfd → driver task → waker → reschedule.
Owns the park point ArcThe loop decides when to block, so it can flush pending submissions immediately before sleeping. MineTokio owns parking; there is no hook to flush the ring before it sleeps, so batching is unavailable and SQPOLL is the only substitute.

The first row is the one the SQPOLL experiment vindicates. Arc gets the same effect — no syscall per operation — by accumulating SQEs and paying one enter for the batch, which costs no extra thread and no extra core. SQPOLL buys the same outcome with a kernel thread; batching buys it for free. That is only possible because Arc's loop decides when to block.

The implementation quality holds up on inspection: a real HTTP/1 parser with a chunked-transfer state machine, generation-tagged slab keys that make stale-completion handling sound, 172 test functions, and CI that runs cargo test --workspace. The io_uring binding is hand-rolled against raw syscalls and mmap rather than the io-uring crate — a deliberate choice to control the submission path.

Caveat

Arc's headline number is not reproducible from the repository

The README claims 102,203 RPS against Nginx's 49,930 at c=256 — a 2.05× win. The benchmark harness that ships in the repo cannot produce a number like that, and no artifact backing the claim is committed.

  • The origin server is http.server.ThreadingHTTPServer from the Python standard library — one OS thread per connection, all contending on the GIL. That tops out in the low thousands of requests per second, not six figures.
  • benchmark/results/ contains only a .gitkeep. The BENCHMARKS.md that once held numbers was deleted in ce78a49.
  • Everything is co-resident on a WSL2 VM with 2 vCPUs: wrk -t8 -c256, Nginx, Arc, and the Python backend all competing for two cores. That is the same failure mode that made the earlier runs in this repository meaningless.
  • The harness gives Arc ARC_WORKERS=1 while Nginx gets worker_processes auto. The asymmetry runs against Arc, but it means the two sides were never configured comparably.

None of this says the architecture is wrong — the code is real and the design is coherent. It says the 2× figure should be treated as unverified until someone reruns it with a backend that is not the bottleneck and a load generator that is not sharing cores with both proxies.

What it took

The four changes, and what each was worth

Nothing about the scheduler produced the win. Every step that mattered removed a cost the adapter was paying on every single operation.

1 · Batch the submissions +58%Queue SQEs and issue one io_uring_enter per scheduler batch. Under Tokio this needs a flusher task that yields, because the runtime owns the park point; natively the loop just submits before it blocks. WhyOne syscall per operation is exactly what epoll costs. Until submissions batch, io_uring has no advantage to spend.
2 · Delete the poll adapter +2×Hand-written state machines advanced straight from CQEs. No future, no waker, no task wakeup per read. WhyCompletion I/O under a readiness API forces a kernel-owned buffer to be copied into a caller-owned one, and forces a park where epoll returns inline.
3 · Register the buffers +66%ReadFixed/WriteFixed against a pre-registered pool, and the buffer a response is read into is the buffer it is written out of. WhyMeasured on the 1 MiB body, where an intermediate copy per chunk had the native build at 51% of Hyper. Removing it took that to 71%.
4 · Size the buffers to the body +76%16 KiB buffers turn a 1 MiB body into 64 serialized read/write round trips. At 64 KiB the same body wins. Why1 MiB went 1,589 → 2,794 rps against Hyper's 2,733. This was the last thing standing between "wins on small payloads" and "wins on all of them".

The bill

What this costs to own

The 2.9× is real and it is measured on an even footing, but it is not free, and the price is not performance work — it is scope.

  • You maintain an HTTP implementation. The native build is HTTP/1.1 only. Its parser, its chunked-transfer framing, its keep-alive and hop-by-hop handling are all code someone now owns. HTTP/2, TLS, upgrades and trailers are not written yet, and each is a real project.
  • You leave the ecosystem. No Tower layers, no Hyper client, no tracing-instrumented middleware. Everything that would have been a dependency becomes a feature request.
  • Memory becomes a floor, not a curve. 267 MB resident at idle, because the buffer pool is registered up front. Hyper starts at 11 MB.
  • Correctness is on you. The generation-tagged completion keys, the buffer ownership rules, the chunked scanner that must not mistake body bytes for a terminator — these are the kinds of bug that a benchmark passes straight through. The 15 unit tests here are a floor, not a proof.

So the honest recommendation is unchanged from the start: this is worth it when the proxy is the product, and hard to justify when it is a component. What did change is the size of the prize — I expected the ceiling to be tens of percent, and it is closer to 3×.
